## ۱) خلاصه اجرایی (TL;DR)

RT-145 در `TODO-openon4net-runtime.md` از ابتدا با علامت ⚠️ ثبت شده: "هیچ API عمومی/Business رسمی اپل نداره؛ نیاز به Mac واقعی+AppleScript یا سرویس واسط شخص‌ثالث با شرایط مبهم". این تحقیق آن فرض را تأیید می‌کند و **هیچ کدی برای RT-145 نوشته نشده** — طبق تصمیم صریح کاربر، فقط همین سند تحویل داده می‌شود.

**نتیجه:** ساخت یک `ChannelProviderPlugin` واقعی و قابل‌فروش در Marketplace برای iMessage، با همان مدل امن/Stateless سایر پلاگین‌های این پکیج (Telegram، WhatsApp، Discord، ...)، **فعلاً ممکن نیست** بدون یکی از دو مصالحه‌ی زیر که هر دو ریسک/هزینه/شکنندگی قابل‌توجهی به Runtime تحمیل می‌کنند.

---

## ۲) چرا iMessage با بقیه‌ی Channel Pluginها فرق دارد

همه‌ی ۶ پلاگین ساخته‌شده در `packages/channel-providers` (RT-140/141/142/143/146/147) یک ویژگی مشترک دارند: سرویس مبدأ (Telegram, Meta Graph API, Google Chat, Discord) یک **REST/Webhook API عمومی و رسمی** با API Key یا OAuth token ساده منتشر کرده. `ChannelProvider` interface این پکیج (`parseInboundEvent(payload)` + `sendMessage(externalSenderId, text)`) دقیقاً حول همین فرض طراحی شده: یک HTTP call ساده، بدون state سمت‌کلاینت، بدون نیاز به سخت‌افزار خاص.

اپل برای iMessage **هیچ‌کدام از این‌ها را ندارد**:

- بدون Business Messaging API عمومی (بر خلاف WhatsApp Business Cloud API یا Meta Send API)
- بدون webhook رسمی برای پیام ورودی
- بدون token/credential که بشود در یک `configSchema` مثل بقیه‌ی پلاگین‌ها (`{key, label, type, required}`) مدل کرد
- پروتکل iMessage (خودِ اپل آن را APNs-backed و end-to-end encrypted نگه می‌دارد) هیچ‌جا مستند رسمی ندارد

## ۳) گزینه‌های واقعاً موجود در بازار/جامعه (بررسی‌شده)

### گزینه A: Mac واقعی + AppleScript/Messages.app automation

مکانیزم: یک ماشین macOS واقعی (فیزیکی یا VM مجاز توسط اپل — نکته‌ی مهم: مجازی‌سازی macOS در غیر سخت‌افزار اپل ناقض EULA اپل است) با `Messages.app` لاگین‌شده روی یک Apple ID، و یک daemon که:

- خواندن پیام‌های ورودی: با poll کردن دیتابیس SQLite محلی `~/Library/Messages/chat.db` (undocumented, بدون schema guarantee بین نسخه‌های macOS) یا با AppleScript event handling
- ارسال پیام: با AppleScript (`tell application "Messages" to send ...`) از طریق osascript

**مشکلات:**

| مشکل        | شرح                                                                                                                                                                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| زیرساخت     | نیاز به یک Mac همیشه‌روشن (فیزیکی یا Mac-in-cloud مثل MacStadium) — کاملاً خارج از مدل Docker/Postgres/Redis فعلی Runtime                                                                                                                                                 |
| شکنندگی     | `chat.db` schema، AppleScript dictionary، و رفتار Messages.app در هر آپدیت macOS می‌توانند بی‌اعلام تغییر کنند — این دقیقاً نوع وابستگی undocumented‌ای است که در بقیه‌ی این مونوریپو (llm-providers, media-providers, channel-providers) تا الان آگاهانه کنار گذاشته شده |
| مقیاس‌پذیری | یک Apple ID = یک "شماره" iMessage؛ برای هر مشتری/سازمان که بخواهد این پلاگین را نصب کند احتمالاً به یک Apple ID/Mac اختصاصی نیاز است (بر خلاف Telegram Bot Token که هزاران بات را روی یک زیرساخت مشترک سرویس می‌دهد)                                                      |
| ToS         | مشخص نیست خودکارسازی Messages.app برای مقاصد تجاری/انبوه ناقض Apple ID Terms of Service باشد یا نه؛ اپل صراحتاً این استفاده را تأیید نکرده                                                                                                                                |
| امنیت       | لازم است credential یک Apple ID شخصی/سازمانی (نه یک API key محدودالدامنه) روی زیرساخت Runtime نگه‌داری شود — با مدل امنیتی فعلی `providerConfigService` (که برای API key/OAuth token طراحی شده) همخوانی ندارد                                                             |

### گزینه B: سرویس واسط شخص‌ثالث (unofficial gateway providers)

چند سرویس تجاری (مثال‌های شناخته‌شده در بازار: sendblue.com، loopmessage.com و مشابه‌ها) یک REST API روی گزینه‌ی A می‌سازند و آن پیچیدگی را از کاربر پنهان می‌کنند.

**مشکلات:**

| مشکل                      | شرح                                                                                                                                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| شفافیت قرارداد            | این سرویس‌ها معمولاً به‌صراحت نمی‌گویند دقیقاً چطور کار می‌کنند (اکثراً همان مدل Mac-farm گزینه‌ی A را پشت صحنه اجرا می‌کنند)، و شرایط استفاده/uptime SLA آن‌ها به مرور زمان تغییر می‌کند                                |
| وابستگی به vendor غیررسمی | هیچ‌کدام partner رسمی اپل نیستند؛ ریسک قطع سرویس بدون اطلاع قبلی (اگر اپل مسیر فنی مورد استفاده‌شان را ببندد) واقعی و مستند در جامعه‌ی توسعه‌دهندگان است                                                                 |
| هزینه                     | این سرویس‌ها per-message یا per-seat قیمت‌گذاری می‌کنند — هزینه‌ای که باید در مدل economics/credits این پروژه (`06-economy-and-marketplace.md`) جداگانه لحاظ شود، چون بر خلاف Telegram/Discord/Google Chat که رایگان‌اند |
| قابلیت تست/راستی‌آزمایی   | بدون credential واقعی (که این تحقیق به آن دسترسی ندارد)، هیچ ادعایی درباره‌ی نرخ موفقیت واقعی این سرویس‌ها قابل تأیید نیست — دقیقاً همان دلیلی که این تسک را از "build" به "research" تبدیل کرد                          |

### گزینه C (رد شده): تلاش برای reverse-engineer پروتکل iMessage خودِ اپل (APNs-level)

این مسیر (شبیه پروژه‌های متن‌باز قدیمی‌تر) رد می‌شود چون معادل حمله به یک پروتکل اختصاصی و رمزنگاری‌شده‌ی اپل است، خارج از دامنه‌ی یک "Channel Plugin" قانونی، و ریسک حقوقی/امنیتی دارد که با اصول این پروژه (کد واقعی، قابل‌تست، بدون فرضیات غیرقابل‌راستی‌آزمایی) در تضاد است.

## ۴) توصیه

1. **RT-145 را در وضعیت ❓ (فعلاً build نکن) نگه دارید.** هیچ‌کدام از دو گزینه‌ی A/B با مدل فعلی `ChannelProvider` interface (stateless HTTP، بدون سخت‌افزار اختصاصی، بدون vendor غیررسمی) سازگار نیست.
2. اگر تقاضای مشتری برای iMessage به اندازه‌ی کافی جدی شد، مسیر پیشنهادی **گزینه‌ی B** است (نه A) — چون حداقل مسئولیت نگه‌داری زیرساخت Mac را از دوش Runtime برمی‌دارد. اما پیش از build باید:
   - یک قرارداد/API-key واقعی از یکی از این سرویس‌ها تهیه و در محیط تست واقعی امتحان شود (نه فرضی)
   - در `ChannelProviderConfigField`/`configSchema` یک هشدار صریح "third-party unofficial gateway — no Apple SLA" به کاربر نهایی نمایش داده شود (شفافیت به مشتری، همان اصلی که در RT-115 برای تأیید فرستنده‌های خارجی رعایت می‌شود)
   - مدل قیمت‌گذاری per-message این سرویس در `plugin economics` جداگانه لحاظ شود
3. تا آن زمان، iMessage از لیست ۷ Channel Plugin ساخته‌شده (Telegram, WhatsApp, Discord, Google Chat, Messenger, Instagram DM + WeChat مستندشده-و-به‌تعویق‌افتاده در RT-144) عمداً کنار گذاشته می‌شود.
